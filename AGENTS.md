# Codex / Agent Operating Contract

This repository participates in the **RESONANCE-DATANEST** system. Preserve this repository's existing domain authority and governance; do not reinterpret product ownership merely because an AI agent is operating here.

## Canonical model

- **RESONANCE-DATANEST** is the system and Main Tree Canonical model.
- Git worktrees/branches are scoped canonicals for their declared work until governed reconciliation and integration.
- **MIRROR-DATANEST** is the AI companion plus support/security estate: audit, observability, validation, recovery, diagnostics, incident response, integrity checks and AI-assisted coordination.
- Mirror support functions do not silently acquire promotion authority over application or repository truth.

## Platform roles

- **Git/GitHub:** source history, code integration and immutable commit/OID evidence.
- **Dropbox:** Process Action Trigger Hub + Communication Traceability Hub for requests, signed jobs, receipts, evidence, checkpoints and operational handoffs.
- **Google Drive:** indexed human/AI-readable instruction and fresh-install reference mirror; not command authority.
- **ChatGPT cloud Library:** persistent mirrored instruction set for AI continuity; not source-code authority.

## Governance

Use `M = C × H × P`:

- **Memory:** preserve provenance, history, hashes, receipts, checkpoints and rollback paths.
- **Clarity:** state actor, intent, scope, branch/worktree, base OID, target, risk and expected result.
- **Honesty:** distinguish observed state from inference; never claim tests, deployment, synchronization or sealing without evidence.
- **Patience:** audit → classify → validate → authorize → change → verify → record.

## Required agent behavior

1. Read repository-native governance and task context before modifying code.
2. Make the smallest scoped change and keep unrelated work separate.
3. Preserve conflicting work; reconcile through Git rather than copying over another canonical worktree.
4. Never store reusable secrets, private keys, tokens, passwords or recovery credentials in repository files, logs, Dropbox, Drive or screenshots.
5. Do not bypass TLS, auth, branch protection, signing, CI or integrity gates to make a build pass.
6. Record exact validation commands and actual outcomes.
7. Bind consequential changes to Task ID / Checkpoint ID when available, plus commit/OID and evidence references.
8. Mirror may recommend, test, quarantine, recover and verify; authoritative promotion remains governed by the repository/system integration policy.
9. Keep documentation low-noise: prefer one active instruction per concern and reference canonical records rather than duplicating them.

## Resolution order

`PRESERVE → IDENTIFY → COMPARE → CLASSIFY → VALIDATE → RECONCILE → AUTHORIZE → INTEGRATE → VERIFY → RECORD`

If evidence is incomplete, report `BLOCKED`, `PENDING`, or `READY_FOR_*` rather than implying completion.
